# ADR 0001 — выбор читателя экспорта по содержимому каталога, JSON-читатель сохранён

- **Status:** accepted
- **Date:** 2026-08-31
- **Run:** `20260831-084236-2-html-telegram-desktop`
- **Deciders:** vlad (владелец), Claude Code (черновик)

## Context

Э2 (`export_reader.py` → `normalize.py` → `blobs.py`) был написан под
`result.json` и `ijson` в предположении, что экспорт Telegram Desktop —
всегда JSON. Перепись Э0 (`probe/01_host_and_export.ps1`,
`probe/02_html_structure.py`) показала: реальный экспорт канала «бухгалтерия»
сделан в **HTML** (`messages.html` + пагинация `messages2.html`, …).
`result.json` в каталоге нет. `segregator backfill` падал на первой же
проверке `_result_path`.

Форма экспорта задаётся человеком в момент выгрузки из Telegram Desktop и
постфактум не меняется. Синтетические фикстуры Э2 (`tests/fixtures/export_min/`)
сделаны в JSON и остаются валидным входом. Live-приём Э6 пойдёт через тот же
`normalize`, поэтому граница «чтение источника» / «нормализация» должна
остаться чистой.

## Decision

Формат экспорта определяется по тому, что физически лежит в каталоге, а не
по конфигу и не по флагу. Новый модуль `src/segregator/ingest/export.py`:
`result.json` есть → JSON-читатель (`export_reader`); иначе `messages*.html`
в корне → HTML-читатель (`html_reader`); иначе `FileNotFoundError` с
упоминанием обоих форматов. `normalize.py` импортирует `iter_messages` /
`read_chat_id` из этого слоя и про формат источника ничего не знает.
JSON-читатель (`export_reader.py`, зона R) **не** переписывается и не
удаляется — поддерживаются оба формата.

## Alternatives considered

| Option | Why not |
|---|---|
| Переписать `export_reader.py` под HTML, JSON выкинуть | JSON — валидный выход Telegram Desktop; на нём стоят фикстуры Э2 и потоковый разбор `ijson`. Потеря рабочего кода ради одного наблюдения. `export_reader.py` в зоне R — правка требует человека на каждый шаг. |
| Флаг формата в конфиге (`EXPORT_FORMAT=html`) | Ещё одна обязательная переменная и класс ошибок «указал не тот формат». Каталог сам себя описывает — `result.json` либо есть, либо нет. |
| Автоопределение внутри `normalize.py` | Ломает границу «нормализатор не знает про формат источника», от которой зависит переиспользование в Э6. |
| Один парсер, определяющий формат по первым байтам файла | HTML и JSON лежат в разных файлах с разными именами; определять по содержимому там, где хватает имени, — лишняя хрупкость. |

## Consequences

**Проще:** добавить третий формат (KSeF XML для 2026+) — ещё одна ветка в
`detect_format`, `normalize` не трогается. Э6 берёт тот же слой.

**Сложнее / цена:** `detect_format` вызывается дважды за прогон (из
`read_chat_id` и из `iter_messages`) — лишний `stat` + `iterdir`, дёшево, но
некрасиво. HTML-читатель грузит страницу целиком в память (`BeautifulSoup`),
в отличие от потокового `ijson` — на многомегабайтных страницах и 6.9 ГБ RAM
это риск (дефект D10). Два читателя — две реализации защиты от выхода за
корень экспорта, которые обязаны совпадать (сейчас совпадают, но связь
неявная).

**Не покрыто:** сам `detect_format` без юнит-тестов (D14); поведение на
каталоге с двумя разными экспортами сразу описано, но VERIFY не пройден.

## Zone impact

Работа осталась в зоне E (`src/segregator/ingest/`, `SPEC.md`, `tasks/`,
`docs/`) плюс T (`tests/`). `export_reader.py` (R) и `cli.py` (I) не тронуты.
`.ai-loop/policy/protected_paths.yaml` менять не нужно: `ingest/export.py`
уже попадает под `src/segregator/ingest/` в зоне E.
