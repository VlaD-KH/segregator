# Spec: Segregator — Э2 «Бэкфилл»

> Статус: активная область спецификации — **только Э2**. Э1 (скелет) выполнен
> и закоммичен. Полное ТЗ проекта живёт отдельным артефактом («ТЗ Segregator»)
> и здесь не пересказывается — этот файл рабочий контракт для текущего этапа.

## Objective

Segregator разбирает Telegram-канал «бухгалтерия» в архив: дерево папок по
месяцам и категориям, SQLite с полнотекстовым поиском, XLSX-реестр для
бухгалтера. Пользователь один — владелец JDG (PL), он же единственный, кому
бот отвечает.

**Э2 строит первый вход в конвейер:** одноразовый разбор исторического
экспорта Telegram Desktop в базу и в content-addressed хранилище блобов.
Live-приём новых сообщений (Э6) пойдёт через тот же нормализатор — поэтому
граница «чтение источника» / «нормализация» проводится уже сейчас.

Экспорт бывает в двух форматах, и оба поддерживаются: **HTML**
(`messages.html`, `messages2.html`, … — так сделан реальный экспорт канала,
установлено переписью Э0) и **JSON** (`result.json` — валидный выход
Telegram Desktop, на нём стоят синтетические фикстуры). Формат выбирается
по тому, что реально лежит в каталоге; `normalize.py` про формат не знает.

Успех = число сообщений и вложений в базе совпадает со счётчиками экспорта,
а повторный прогон не создаёт ни одной новой записи и ни одного нового файла.

### Карта этапов (капабилити-мапа задана ТЗ, не изобретается здесь)

| id | Ответственность | Зависит от |
|---|---|---|
| Э1 skeleton | конфиг, схема БД, CLI, логирование | — |
| **Э2 backfill** | **экспорт → messages/blobs/attachments** | **Э1** |
| Э3 extract | текстовый слой, OCR, поля | Э2 |
| Э4 classify | каскад прецедент → правило → LLM | Э3 |
| Э5 route | два дерева на диске | Э4 |
| Э6 live | aiogram, карточки подтверждения | Э2 |

Порядок сборки: Э1 → **Э2** → Э3 → Э4 → Э5 → Э7, при этом Э6 подключается
после Э2, потому что переиспользует нормализатор.

## Tech Stack

Python 3.12.10, Windows 11. Уже в проекте: `pydantic` / `pydantic-settings`
2.12 (конфиг), `typer` 0.25 (CLI), `structlog` 26.1 (логи), `httpx` 0.28,
`aiogram` 3.28 (Э6), `pytest` 9.0. Хранилище — `sqlite3` из stdlib, WAL,
FTS5. Для Э2 добавляются две зависимости: **`ijson`** (потоковый разбор
JSON-экспорта) и **`beautifulsoup4`** (разбор HTML-экспорта, бэкенд
`html.parser` — чистый Python, без компиляции под iGPU-машину).

Модель на будущее: `gemma-3-4b-it-Q4_K_M.gguf`, локально, класс 4B. Внешних
LLM-API в проекте нет.

## Code Style

Русские докстринги и комментарии, английские идентификаторы, польские
доменные термины в данных (`koszty`, `wg-daty-dokumentu`). Комментарий
объясняет **почему**, а не что. Пользовательский вывод CLI — по-русски.

```python
def store_blob(archive_dir: Path, source: Path) -> BlobRef:
    """Положить файл в content-addressed хранилище. Идемпотентно."""
    digest = _sha256(source)
    target = archive_dir / "blobs" / digest[:2] / digest[2:4] / f"{digest}{source.suffix}"
    if target.exists():
        # Тот же sha256 — тот же байт-в-байт файл. Второй копии не создаём,
        # но вызывающий получит was_new=False и заведёт вторую ссылку.
        return BlobRef(sha256=digest, path=target, was_new=False)
    target.parent.mkdir(parents=True, exist_ok=True)
    # Через временный файл: прерванный прогон не должен оставить обрезанный блоб.
    tmp = target.with_suffix(target.suffix + ".part")
    shutil.copyfile(source, tmp)
    tmp.replace(target)
    return BlobRef(sha256=digest, path=target, was_new=True)
```

## Testing Strategy

`pytest`, тесты в `tests/`, всё через `tmp_path` / `monkeypatch`. Фикстура
`isolated_project` (`tests/conftest.py`) — единственный источник путей; ни
один тест не ссылается на настоящий `EXPORT_DIR` и ни на что под `Downloads`.

Уровни: юнит на чистых функциях (sha256, резолв путей), интеграционные на
CLI через `typer.testing.CliRunner`, плюс инвариантные тесты контура данных
(`tests/test_data_boundary.py`), которые обязаны падать при регрессе.

Каждая синтетическая фикстура регистрируется в `tests/fixtures/manifest.json`
с `"synthetic": true` — незарегистрированный файл роняет
`test_fixtures_are_all_marked_synthetic`.

Порог: любое правило классификации и любой экстрактор доказываются тестом.
Для Э2 — приёмка ниже проверяется тестами, а не глазами.

## Boundaries

**Always**
- Считать деньги, налоги и взносы детерминированным Python, покрытым тестами;
  модель классифицирует и объясняет, но не арифметику.
- Прогонять субагента `boundary-guard` перед каждым коммитом, который трогает
  `src/`, `agents/` или `tests/`.
- Держать все пути, пороги и адреса в конфиге; ни одного абсолютного пути в коде.
- Маскировать PESEL, IBAN и номера карт везде, кроме самого генерируемого
  официального документа.
- Резолвить любой путь, пришедший из данных, и проверять, что он остался под
  корнем экспорта.

**Ask first**
- Новая зависимость (`pip install` — правило `ask` в `.claude/settings.json`).
- Изменение схемы БД (новая миграция).
- Любой новый сетевой вызов — с объяснением, почему он не рвёт контур.
- Изменение налоговых констант — только через `pl-tax-checker` со ссылкой
  на первоисточник.

**Never**
- Отправлять содержимое документа, извлечённое поле или имя файла из архива
  за пределы этой машины — ни в облачную модель, ни в телеметрию, ни в переписку.
- Обращаться к LLM не на loopback (проверяется валидатором конфига).
- Класть настоящие документы в `tests/fixtures/`.
- Писать содержимое документов в логи — только идентификаторы, категории,
  уверенность.
- Подавать что-либо в KSeF, ZUS или e-Deklaracje: система готовит файл,
  отправляет человек.
- Удалять данные раньше срока хранения (5 лет от конца календарного года,
  в котором наступил срок уплаты налога).

## Success Criteria

Приёмка Э2 (ТЗ §13), всё проверяется тестами:

1. **Счётчики сходятся.** Число строк `messages` = числу сообщений в
   экспорте; число строк `attachments` = числу вложений. Проверяется на
   обеих фикстурах — `export_min/` (JSON) и `export_html/` (HTML).
2. **Дедупликация.** Один и тот же файл, отправленный дважды, даёт **один**
   блоб на диске и **две** строки `attachments`.
3. **Идемпотентность.** Второй прогон `backfill` подряд: ноль новых строк,
   ноль новых файлов, ненулевой выход не считается ошибкой.
4. **Path traversal отбивается.** Ссылка вложения `../../../evil.pdf` или
   абсолютный путь в экспорте (в поле `file` JSON либо в `href` HTML) не
   приводит к записи за пределами корня экспорта.
5. **Битый экспорт не роняет прогон.** Отсутствующий на диске файл вложения
   пропускается с предупреждением; прогон доходит до конца и сообщает счётчик
   пропусков.
6. **Память.** JSON-экспорт разбирается потоково через `ijson` (не
   `json.load`); HTML — постранично, `messages*.html` по одной, без сборки
   всей переписки в память.
7. **Выбор формата.** `result.json` есть → JSON-читатель; иначе `messages*.html`
   в корне → HTML-читатель; иначе `FileNotFoundError` с текстом про оба
   формата. `normalize.py` формат не различает.
8. Все тесты Э1 и ранее написанные тесты Э2 остаются зелёными.

## Open Questions

1. **`ARCHIVE_DIR` не выбран.** C: заполнен на ~92%, второго диска нет.
   Требуемый объём ≈ 1×S (hardlink) или 2×S (копии), где S — вложения экспорта
   после дедупликации; S даст перепись. (Э0 показала S ≈ 40 МБ — не проблема.)
2. **Копии или hardlink в дереве (решение Э5, но влияет на выбор диска).**
   Рекомендация — hardlink: вдвое меньше места и снимает требование WSL2,
   потому что hardlink на NTFS не требует режима разработчика, в отличие от
   симлинков. Ждёт подтверждения.
